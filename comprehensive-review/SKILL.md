# 统一评审框架 (Comprehensive Review)

## 输出模式选择 🆕 v1.30.0

根据触发词选择输出模式：

| 触发词 | 模式 | 输出内容 |
|------|------|------|
| `全面评审` / `Rubrics+红蓝` | **完整模式** | 决策三角(3s)→Rubrics评分→红蓝互辩→整合结论→理解债闸门 |
| `红队审查` | **纯红队** | 决策三角(3s)→3个致命疑点→一句话整合结论 |
| `快速评审` | **轻量模式** | 决策三角(3s)→红队批判(3疑点)→一句话整合结论 |

**决策三角（所有模式必含）**：在输出最顶端，一行内给出方向性判断：

```
✅ 可行 — {一句话理由}
⚠️ 有条件可行 — {条件} — {理由}
❌ 不可行 — {致命原因}
```

**🆕 通信偏好 v1.30.1**：当向用户解释新的抽象概念（如 refute pass、MoA、正交性）时，**先用一个通俗易懂的生活化例子说明**，再进入技术细节。用户反馈"没看懂多一层的意思，举个通俗易懂的例子吧"——抽象定义无法替代具体类比。饭后去哪吃饭、三个医生会诊、考试三道题——只要是日常场景，都比流程图好懂。

## 触发条件

当用户要求对一份分析/报告/决策建议做**全方位质量评估**时加载。

触发词：**全面评审** / **Rubrics+红蓝** / **深度复盘** / **综合审查**

**文章链接场景**：当用户将上述触发词附加到文章链接请求时（如"全面评审这篇文章"），自动走完整流程——先独立分析文章（不加建议）→ 对照已有 skill 框架 → 红蓝互辩 → Rubrics 评分 → 收窄交付。不需要用户额外提醒"别忘了红蓝队"。

**🆕 批评者角色（v1.31.0 · 2026-07-28 算力手册评审教训）**：全面评审的核心定位是**批评者，不是学生**。当评审一份用户指定的文件时：
- ❌ 不要提炼"学到了什么""有什么启发""萃取模式"
- ✅ 找漏洞、找矛盾、找缺失、找改进空间
- ✅ 先用被评审文件自身的引用体系验证（如附录/脚注/来源表），再判断"来源缺失"——文件可能有 `[数字]→附录B` 系统而你漏看了
- ✅ 动用 web_search 交叉验证文件中的关键数字和事实声明
- 如果文件找不到，如实说找不到，请求用户直接提供——不要基于印象或常识替代评审

**评分锚点 🆕 v1.30.0**：6 分为"及格线"——每个维度的 6 分含义如下。低于 6 分 = 存在可操作的缺陷。

| 维度 | 6 分锚（及格线） | 低于 6 分的具体含义 |
|------|------|------|

| 实际可用性 | 用户读完能做出一个具体行动决定 | 结论模糊，无可执行步骤 |
| 意义提炼 | 有超越罗列的判断，区分了已知与未知 | 纯数据罗列，无独立洞察 |

## § 执行计划容器匹配检查（v1.18.0）

**在分析类全面评审的整合结论中，如包含执行计划（如"Layer 1 → MEMORY / Layer 2 → X / Layer 3 → Y"），必须在输出前运行此容器匹配自检：**

```
□ 该内容是否含评估结论/状态信息（如"有价值""stars=0""已决定X"）？
  → 是 → 不透支 MEMORY。选 evaluated-projects 或跳过 Layer 1。

□ 该内容三月后是否仍成立？
  → 否 → 不选 MEMORY。MEMORY 是跨会话的持久事实存储，不是临时笔记。

□ 该内容删除后是否影响系统运行？
  → 否 → 不选 MEMORY。留 evaluated-projects 索引足矣，需要时 Ctrl+F。
```

**三个问题任一答"否"→ Layer 1 不选 MEMORY。默认归宿：evaluated-projects.md。**

> 此检查源自 2026-07-14 gate.cat 评审的两次容器匹配错误——全面评审分析了内容质量，但未审查执行计划的容器选择。详见已知陷阱「分析-执行断层」。

## § 审查者模型选择（v1.19.0）

**审查者不应比被审查者弱一级。** 当全面评审的评估对象是一个 LLM 生成的报告时，评估模型应与生成模型有认知差异：

| 被审查报告的生成模型 | 推荐审查模型 | 原因 |
|------|------|------|
| deepseek-v4-flash | deepseek-v4-pro | 同厂商不同架构强度，指令遵循和逻辑审查更强 |
| deepseek-v4-pro | deepseek-v4-flash 或 MiniMax-M3 | 不同认知模式（精确匹配 vs 跨域关联），正交性优先 |
| 任意单一模型 | 三路并行（Flash+Pro+M3） | dense/dense/MoE 三个正交维度，最高审查强度 |

**不推荐同模型自审**——生成者和审查者共享推理盲区、格式倾向和幻觉模式，审查结论可信度打折。

## § 来源检查前置（v1.31.1 · EarlETF 评审教训）

**在断言"无来源/无引用"之前，必须先搜索以下模式：**

1. **数字引用标记**：`[1]` `[2]` `[数字]` → 可能指向文末附录
2. **附录/参考文献关键词**：`附录` `参考文献` `Reference` `出处` `来源`
3. **超链接**：文中可能通过命名锚点/URL 隐式引用

**反例**（2026-07-28）：评审时结论称"来源全无、不可验证"。实际文中有 `[数字]` 编号引用指向附录 B，评审时未搜索这些模式。用户纠正后才修正。**修正**：评审工作流 Step 0 增加"文档结构扫描"——先确认引用机制的**形式**（URL？编号引用？附录？），再对源标注打分。

**成本考量**：单次切换 Pro(¥0.05) vs Flash(¥0.01) 的价差 ¥0.04，BTC 评估 3次/天 = ¥0.12/天。审查不可靠的隐性成本（错过质量信号）远超 ¥0.12。

> 此规则源自 2026-07-14 BTC Rubrics 评估模型讨论——被审查报告用 Flash 生成，审查者也是 Flash，16% 的 API 连接失败率叠加同质化审查风险。MiniMax 在结构化审计任务中落选（指令遵循弱于 Pro），但在三路并行中保留跨域知识审查的角色。

| | 单独 Rubrics | 单独红蓝 | **统一评审** |
|------|:--:|:--:|:--:|
| 评分 | ✅ | ❌ | ✅ + 验证 |
| 批判 | ❌ | ✅ | ✅ + 动态规则 |
| 互补 | — | — | ✅ 两路交叉验证 |
| 整合结论 | ❌ | ❌ | ✅ 可信度评级 |

## 🆕 黄金测试双重验证追问（v1.32.0 · QuantSkills 教训）

当全面评审一方声称某项目/因子的"验证全部通过"时，红队必须追问：

> **"通过的是什么？格式正确性？计算正确性？还是投资收益？"**

- **计算正确性** = 代码无 bug、未来函数未渗透、IC 值在合理区间——这是**及格线**，不构成推荐理由
- **格式正确性** = 输出格式符合规范——这是**最低门槛**，通过≠有效
- **投资收益正确性** = 因子在实际策略中产生了统计显著的超额收益——这才是**推荐理由**

**触发条件**：评审对象含"验证通过""all tests passed""X/X 通过"等表述时，红队段必须追问验证的是什么层次。

| 声称 | 红队追问 |
|------|------|
| "296/296 因子验证通过" | "通过的验证层级是什么——计算正确性≠投资收益" |
| "IC 显著" | "IC 衰减曲线显示有效期多长？子样本分片的一致性如何？" |
| "未来函数检查通过" | "检查做了什么——是规则类约束还是统计测试？" |

**来源**：quantskills/quantskills 文章评审发现，文章声称"800 个因子全部通过验证"但未提供任何一个因子的实际 IC 数值或策略级验证结果——"全通过"可能只意味着代码跑通了。

对话中实现真正三模型正交审查的最简方式——在全面评审前加 `/moa`：

```bash
/moa 全面评审这份报告
```

MoA review 预设（Flash+M3 参考 → Pro 聚合）提供真正的三模型正交性（多模型并行、独立上下文），comprehensive-review skill 提供 Rubrics 八维 + 红蓝互辩 + 决策三角格式。两者叠加 = 格式规范 + 真正正交。

若未配置 MoA（或 MoA 参考模型不可用），对话场景降级为单模型角色扮演，必须标注：

> ⚠️ 本次为单模型模拟，未经独立模型/独立上下文验证。

## 财经溯源时间窗口门禁（v1.2.0新增 — 2026-07-03 英伟达翻车教训）

当用户要求溯源财经文章/事件的可靠性时，**强制先执行时间窗口锁定**，不可跳过：

### 时间窗口锁定（Step 0 — 溯源启动前必做）

1. **确定事件时间**：文章发布日期 ± 72h 窗口
2. **搜索一手官方源**：公司博客 / PR Newswire / CFO联署公告 / SEC 8-K filing
3. **搜索独家爆料**：The Information / Bloomberg / Reuters 原创新闻
4. **锁定后**：确认「最近72h有没有新事件」——有→以此为锚；无→扩展到更早分析

**门禁不通过（跳过1-3直接搜分析文）→ 溯源结论不可发布。**

翻车案例（2026-07-03）：分析微信公众号"英伟达的算力贷"时，跳过了NVIDIA 7月1日CFO联署官方博客+The Information 7月1日独家爆料，直接搜到了Tomasz Tunguz几周前的旧分析，导致结论完全相反。

## 系统设计方案评审（v1.2.0）

Rubrics 框架同样适用于系统设计方案评审（如日报差异化方案、架构改造提案）。维度需做适配：

| 原始维度 | 方案评审对应 | 评估要点 |
|------|------|------|
| ① 事实正确性 | 对现状的诊断是否准确 | 是否基于代码/日志/实测数据？ |
| ② 覆盖度 | 是否覆盖了所有关键问题域 | 有无遗漏的维度（如LLM prompt层）？ |
| ③ 证据支撑 | 每条建议是否有根因支撑 | 是否引用了具体数据/日志/用户反馈？ |
| ④ 推理严谨性 | 因果链/参数推导是否清晰 | 阈值有无依据（如"衰减50%"为什么是50%）？ |
| ⑤ 格式合规性 | 方案结构是否完整清晰 | 落地步骤是否有序？ |
| ⑥ 来源类型 → 可维护性 | 改动侵入性/风险 | 是否可能引入新bug？ |
| ⑦ 实际可用性 | 能否直接落地 | 改动量多大？是否需要新依赖？ |
| ⑧ 意义提炼 | 是否超越了表面修补 | 有没有系统性解决根因而非打补丁？ |

|**适用场景**（2026-07-03 实例）：日报差异化方案评审——衰减+轮换+prompt引导，红队识别出衰减参数拍脑袋、去重误杀风险、配额与质量冲突三个疑点。|

## 三模型并行评审 (v1.18.0 · ai-berkshire 启发)

**来源**：xbtlin/ai-berkshire 的 4 Agent 并行分析模式 + 本系统 2026-07-13 落地。

当需要最高质量审查时，不使用单一 delegate_task（同模型串行），而是拆分三个独立 cron，各自绑不同模型同时运行：

| 角色 | 模型 | 架构 | 审查目标 |
|------|------|------|------|
| 🔴 红队数据审计 | `deepseek-v4-flash` | Dense | 数据准确/逻辑自洽/区间可复现 |
| 🔄 反共识压力测试 | `deepseek-v4-pro` | Dense | 发散思维/反事实推演/死因假设 |
| 🌐 宏观映射检验 | `MiniMax-M3` | MoE | 跨域知识/外部一致性/SOX映射 |

**正交性来源**：
- Flash vs Pro：认知模式不同（精确规则匹配 vs 深度推理）
- DeepSeek vs MiniMax：架构不同（dense vs MoE），训练数据不同
- 三个 cron 独立上下文，不共享推理链

**实现**：三个 cron 同 schedule（如 `20 9 * * 1-5`），读同一个 trajectory 文件，各自输出 8-10 行紧凑结论。见 `references/parallel-review-architecture.md`。

**对话场景替代方案**：对话中无法复现三模型并行（delegate_task 不支持 per-task 模型）。两种降级：
1. **对话模式**：主进程内分三段输出（认知多样性保留，模型多样性丢失）
2. 若分析已写入 trajectory → `cronjob run` 触发三个 cron 手动跑

**⛔ 对话场景输出格式规则（v1.20.0）**：在对话中以"三路审查"格式输出时，必须遵守以下免责声明：

- 若为**真实三路并行**（三个 cron 独立触发）：标注「✅ 三模型正交审查已完成」
- 若为**对话模拟**（单模型扮演三角色）：标注「⚠️ 本次三路审查为单模型模拟，未经独立模型/独立上下文验证。若需真正正交审查，可回复「全面评审」触发 cron 并行审查。」
- **禁止**在模拟三路审查的底部标注「本分析未经红队独立审查」——因为格式中已经嵌入了一个名为🔴红队的段落，读者会自然追问"那段红队算什么"。模拟红队≠独立审查员，声明必须在行文顶部就区分清楚。

> 反例（2026-07-14 机器人ETF午间审查）：输出标题为"三路审查"，正文含🔴红队/🔄反共识/🌐宏观映射三段，底部却标注"本分析未经红队独立审查"——用户立即指出自相矛盾。根因：单模型角色扮演的红队分析本质上仍是同模型生成，与真实独立审查有认知同质性差距。

**适用场景**：
- 盘前/盘后的自动化评审（cron 模式）
- 系统设计方案/架构提案的深度评审
- 需要真正正交视角的高风险分析

## 两步法 vs 一步法（v1.3.0新增 · 元模式）

当用户要求对文章/方案同时做「分析建议」和「质量评审」时，**分离两步优于合并一步**。

**根因**：生成和批判共用同一模型时，批判思维会污染生成思维——产出的建议不是因为全面所以收敛，而是因为不敢发散所以没尝试。这正是 LoopCoder 两圈法则在方法论层面的映射。

**推演**：
- 一步法：同时做评审+建议 → 评审结果里不会出现"建议过度扩展"——因为建议是自己刚生成的，大脑无法同时切换到批判模式
- 两步法：先大胆建议 → 红蓝队独立批判 → 收窄——被砍掉的和没被提出的，不是一个量级

**适用场景**：
- 用户发了外部文章要分析 → 先独立分析提建议 → 再触发全面评审
- 用户直接说"全面评审并给方案" → 主动问："先让我分析文章提建议，再走红蓝队评审？"

**翻车案例**：英伟达算力贷溯源——Grace 两步法找到 NVIDIA 7/1 官方博客，隐序一步法搜到旧分析就下结论。时间窗口门禁强制了两步分离。

## 外部文章修正（v1.1.0新增）

当用户发送外部文章链接（如 EarlETF、券商研报、行业分析）时，若文章内容对当前分析有修正作用，应在**整合结论之前**将其纳入：

1. 提取文章中与当前分析直接相关的判断
2. 对照自己的分析，标注哪些被验证、哪些需修正
3. 修正后的结论写入整合总结

**典型场景**（2026-07-02 实例）：科创50短线分析完成后，EarlETF 文章指出「A股半导体无法脱离日韩美股走出独立行情」→ 修正了交易前置条件（增加"等待美股企稳"的门槛）。

## 理解债前置（v1.27.0 · 协作纪律）

**在文章评审类全面评审启动前**，如果当前会话已经累积了多轮对话、多个任务线、或跨 session 的 compacted context，须先执行「理解债清理」：

1. **问自己**：当前任务依赖的前置条件中，有哪些是"我以为我知道但实际可能错的"？
2. **查活文件**：compacted context 是旧快照——SOUL.md / MEMORY / USER.md 可能已在两次会话之间被修改。先读活文件，再读快照。
3. **标未确认**：若有涉及数字/事实/数据源的前置判断未经验证，在全面评审输出中显式标注为"基于未验证前提"。

> 最危险的理解债不是"知道不知道"，而是"不知道自己在用错数据"（如 2026-07-23 科创50 trajectory 的 `close_last=2.016` vs 实际昨收 `1.955`，所有下游分析基于错数运行）。

## Borg 交叉验证（v1.29.0 · 2026-07-27 · leader skill 教训）

当全面评审涉及 GitHub 开源项目且有 Borg 评估结论时，在整合结论后追加「Borg vs 人工」对照：

| | Borg 评估 | 人工评审 |
|------|------|------|
| 评分依据 | 关键词+stars+盲区+管线 | 源码深度+方法论+社区背书 |
| 准确度 | 英文技术栈准，中文方法论失明 | 覆盖全面 |
| 执行 | Gate→自动同化（机械） | 考虑环境兼容性+使用场景 |

**收敛规则**：两者一致的部分 = 确定结论；不一致的部分 = 需人工判断（Borg 不审查使用场景适配性）。

## 辅助知识条件路由（v1.37.0 · 按对象属性加载，非固定清单）

> 来源：Beileian/comprehensive-review 教学版 CORE.md §6（对应本地 v1.37.0 快照）。

评审对象不同，需要加载的辅助知识不同。按三维判定：

```
第一维：对象类型 → 基础知识集
  外部项目/仓库 → 工程模式库（资产对照）
  系统方案 → 工程模式库（爆炸半径/回滚）
  分析报告 → 陷阱表（数字验证）
  故障排查 → 诊断模式 + 责任层分配（agent行为/状态投影/设计缺口/基准不匹配/文档卫生）

第二维：行业 → AI/半导体类 + 供应链方法闸门；其他显式声明不适用

第三维：内容性质 → 含数字断言 + 陷阱表主动检查；纯设计不叠加
```

**判定先行 + 按需加载 + 加载声明可审计**（"本次加载 X+Y，未加载 Z 因为……"）。

```
|:--:|------|------|:--:|------|
| 1 | {判断} | {如果错了会怎样} | 低/高 | ✅ 已解决（证据）/ ⚠️ 未解决（原因） |

> 若全部关键判断均已经过人工/实盘验证 → 标注「✅ 本次无未确认关键判断」
```

**规则**：
- 至少列出 1 条。无法识别任何未确认判断 = 最大的理解债风险。
- 判断来源包括：LLM 推理结论、自动计算的指标、自动生成的定档、自动选用的方法论框架
- 不阻塞交付——闸门是"标记"而非"拦截"。目的是让用户意识到"这个结论我没验证过"

**自动预验证原则（v1.37.0 · 来源：教学版 CORE.md §5）**：
- 验证执行可自动（读文件/grep/实测）——低成本直接解决，高成本尝试一次
- **验证失败不编造**——标"保留为未确认"，不硬填结论
- **"不可达"必须带实测证据**——可审计，单次失败不判永久不可达
- 保留人工决策：验证优先级筛选 + "不可达则接受/换方案"

> **最危险的理解债（2026-07-23 实战教训）**：不是"知道不知道"，而是"不知道自己在用错数据"。科创50 trajectory 的 `close_last=2.016` 实际昨收 `1.955`，所有下游分析（deviation_20、刘晨明离场阈值、入场区间）基于错数运行了一整天。如果红队没在午盘手动发现，这个错会静默累积到下一周。**闸门不仅要标记"我们不确定的判断"，还要标记"我们以为确定的数字"——后者更难发现，伤害更大。当数据源有多个候选（K线 close vs quote.last_close），且其中一个是隐性错误源（ETF K线返回NAV而非市场价）时，即使判断看起来"确定"，也应该在闸门中追问"这个数字从哪来的"。**

## 核心纪律（v1.37.0 · 通用化六条）

> 来源：教学版 CORE.md §7。第 1-5 条本地已有对应章节，此处统一索引；第 6 条为新增。

1. **先独立分析，再加建议**（两步法）——生成与批判共用同一模型时，批判污染生成；先大胆建议，再红蓝独立批判，收窄
2. **来源检查前置**——断言"无来源"前先搜数字引用标记/附录/参考文献/超链接（可能只是引用形式没识别）
3. **黄金测试追问**——"验证通过"要追问层次：格式正确性？计算正确性？投资收益？——及格线≠推荐理由
4. **验证路径一致**——"无法复现"前确认评审者验证的数据路径 = 被审对象诊断的路径（展示层 vs 消费层）
5. **先查上游再下结论**——任何"X 没做 Y"类断言，先验证数据源，再给结论
6. **修复在最持久的层**（🆕）——问题先归类责任层（agent 行为/状态投影/authoring 缺口/基准不匹配/文档卫生），修复最低持久层，禁止只在聊天里道歉

## 🆕 多路合成实操经验（v1.36.0 · 2026-08-02 科创50ETF 盘前管线注入）

> 来源：四板块（科创50/银行/国电/机器人ETF）多路审查合成管线的 8 天实战，
> 含 3 次真实跑偏事故。以下三条是本系统用事故换来的教训，适用于任何
> 「多路独立审查 → 合成器汇总」架构。

### 1. 内容类型校验（P0 — 防止审查输出角色错乱被静默消费）

**问题**：合成器/下游消费多路审查输出时，只检查「文件是否存在」，不检查
「内容类型是否匹配角色」。当某路审查跑偏（如反共识输出了红队格式），
合成器会把错误角色的内容当正常输入消费。

**实测案例**（科创50反共识 2026-07-24 ~ 08-02）：
- 反共识 cron 输出文件存在（120KB，UPSTREAM_STATUS 显示 OK）
- 但内容开头是「🔴 红队数据批判 · FT-CODE」——角色完全错乱
- 合成器零检测，把红队内容当反共识用了 10 天
- 三路认知正交退化为两路（Flash + M3），架构哲学直接失效

**修复模板**（synthesize_*.py 的 UPSTREAM_STATUS 段）：

```python
CONTENT_MARKERS = {
    "devil": ["反共识", "死因假设", "被忽视的风险", "反面证据"],
    "macro": ["宏观映射", "宏观因子", "跨市场", "global_macro", "macro_mapping"],
}
MISMATCH_BLACKLIST = {
    "devil": ["红队数据批判", "FT-CODE", "数据批判", "数据审计"],
    "macro": ["Refute Pass"],
}

def check_content_mismatch(name, response_text, role_key):
    head = response_text[:3000]  # 跑偏通常在开头
    own_markers = CONTENT_MARKERS.get(role_key, [])
    if any(m in head for m in own_markers):
        return False, ""  # 角色标志词命中 → 正确（标题串扰不阻断）
    blacklist = MISMATCH_BLACKLIST.get(role_key, [])
    for bad in blacklist:
        if bad in head:
            return True, f"含「{bad}」且无角色标志词——疑似角色错乱"
    return True, "未含角色标志词——疑似空跑或跑偏"
```

**判定规则**：own-marker 命中优先（标题串扰放行）；own-marker 缺失时黑名单生效。

### 2. 审查者角色约束（P1 — prompt 必须有输出格式硬约束）

**问题**：审查类 cron 的 prompt 若只有「审查内容」而无「## 输出」格式约束，
模型会自由发挥甚至跑偏到其他角色。

**实测案例**（机器人ETF宏观 2026-08-02）：
- prompt 仅 342 字符，无输出格式约束
- M3 把「宏观映射」任务误解为「审查红队+反共识推理漏洞」（即 Refute Pass 职责）
- 输出 Refute Pass 报告而非宏观映射报告，合成器判定「宏观缺失」降级 2/3 路
- 同源风险：银行/国电宏观 cron prompt 同为 v1.1.0 无约束（当天运气好未跑偏）

**修复模板**（审查 cron prompt 末尾）：

```
## 输出（严格按此格式，禁止输出其他角色格式）

🔄 {角色名} · {YYYY-MM-DD}
死因假设: {...}
被忽视的风险: {列表}
反面证据: {列表}

⚠️ 你不是{其他角色}。禁止输出「{其他角色格式关键词}」内容——那是{角色} cron 的职责。
```

**关键**：`## 输出` 段必须明确报告格式 + 明确禁止的角色格式，双约束缺一不可。
科创50 prompt 升级后（320→813 字符），手动触发验证产出正确反共识格式。

### 3. Refute Pass 第四层（P1 — 专门打破三路共识盲区）

**问题**：三路审查（红队查数据、反共识挑格式、宏观找利空）可能共同确认同一个
方向，无人系统性挑战「主流结论本身」。

**实测案例**（科创50 2026-08-02 Refute 发现）：
- 红队查数据不挑战方向，反共识挑格式不挑战结论，宏观映射找利空不查利多
- 三路全部「确认 bearish」，无人讨论 7/31 +3.54% 反弹是否隐含转折信号
- 教科书级确认偏误——三路独立但同向，正交性失效

**设计**：三路审查之后加第四路「审查者的审查者」（Refute Pass）：

```
红队(Flash) ──┐
反共识(Pro) ──┼──→ 合成器 ──→ 微信推送
宏观(M3) ────┘        ↑
                Refute Pass(Pro)
                专门挑三路共同的推理盲区
```

**Refute Pass 的职责**：逐条检查每个审查者的结论，找推理层面的错误——
循环推理、不对称质疑、因果倒置、选择性引用；以及最关键的：三路共同的认知盲区。
若三路全部确认同一方向，Refute 必须主动问「如果这个方向是错的，最可能因为什么？」
