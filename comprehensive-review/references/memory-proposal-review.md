# 记忆预分类提案全面评审实例（2026-07-31）

## 背景

cron「记忆+Skill健康度·隔日检」（7eb27e54d9c0，no_agent 脚本模式）输出 3 条 MEMORY 预分类提案，用户要求「全面评审以上cron输出的提案」。评审对象是 **cron 输出本身的质量**，不是投资分析——系统设计提案评审适配版。

## 三条提案与裁定

| # | 脚本类别 | 条目摘要 | 实际判定 | 根因 |
|:--:|:--:|------|:--:|------|
| 1 | 🟢 升格SOUL | cron空输出排查必须：①先查上游数据源(DB/API/RSS)… | ❌ **假升格** — 应删除/合并 | SOUL.md §cron异常排查铁律 rule 4 已有等价规则（先查上游再下结论）。条目自身结尾就写着"SOUL.md已加cron异常排查铁律"，但「铁律」二字命中升格触发词，把**状态说明**翻转成了**升格提议** |
| 2 | 🟢 升格SOUL | 用户对细节敏感——typo（"crob"→"cron"）被一眼发现… | ❌ **容器错配** — 应移入 USER 或删除 | 这是用户特征（USER 域），不是行为规则（SOUL 域）。条目含「铁律标题」中的"铁律"二字，命中升格分支 |
| 3 | 🔵 移入USER | 用户偏好：盘前数据过时时主动建议重跑四路审查… | ✅ 方向正确 | 纯用户偏好，USER.md 无重复，移入有效 |

**通过率：1/3**。仅 #3 可执行，#1/#2 若照 cron 引导语「说『执行…提案』即可批量落地」执行，SOUL.md 会被写入重复规则、逼近 8KB 红线。

## 根因：脚本查重缺陷（memory_health_check.py v2.6.0）

```python
if any(kw in text for kw in ['禁止', '红线', '铁律', '硬规则', '绝对', '永不']):
    snippet = text[:30].strip()          # ← 只取前30字符
    if snippet and snippet in SOUL_TEXT: # ← 逐字包含判断，非语义判断
        continue  # 已存在——跳过升格
    cat, reason = '🟢 升格SOUL', '行为规则/纪律'
```

三个具体缺陷：
1. **字面前缀匹配**：`text[:30] in SOUL_TEXT` 要求条目前 30 字符**逐字**出现在 SOUL.md 中。语义等价但措辞不同 → 漏过（#1 案例）。
2. **触发词位置敏感**：升格判定只看「条目是否含『铁律/红线/禁止』等关键词」，不看关键词的**语义角色**——"SOUL.md已加…铁律"是状态说明，却被当成规则内容触发升格。
3. **"预估节省"是容器迁移幻觉**：MEMORY 删 170 字、SOUL/USER 增 170 字，系统每轮注入总量不变，净节省为 0。

## 评审方法论（可复用）

1. **先读活文件**：评审前读 `~/.hermes/memories/MEMORY.md`、`~/.hermes/memories/USER.md`、`~/.hermes/SOUL.md` 实际内容，不依赖系统提示注入副本（注入副本可能与文件不同步）。
2. **逐条对照目标容器**：对每条提案问「目标容器是否已有语义等价内容？」有 → 提案方向应为删除/合并而非升格/移入。
3. **核查分类触发器**：确认触发分类的关键词在条目中扮演什么角色（规则内容 vs 状态说明 vs 反例）。
4. **裁定按条给出**：采纳/拒绝/改向（如 #2 改移 USER），不批量背书。
5. **顺手修脚本**：发现查重缺陷 → 建议用关键词交集检测替代字面前缀匹配（P0）。

## 后续动作

- P0：修 `memory_health_check.py` 升格查重——关键词交集检测（提取条目核心词如「先查上游/数据源/静默失败」与 SOUL.md 段落做重合度判断），而非 `text[:30]` 字面匹配。
- P1：分类器加「目标容器现状检查」——提案生成前读 SOUL.md/USER.md 全文判定语义重叠。
- P1：cron 输出引导语从「说『执行…提案』即可批量落地」改为「逐条核验后再执行」——批量执行引导语让错误分类随批量指令一起落地。
