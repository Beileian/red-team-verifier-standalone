# 大轰炸周精确裁军方法论

> 来源：2026-07-11 阶段六红蓝评审
> 战史映射：1944年2月大轰炸周——从分散炸50+工厂→集中炸石油/交通枢纽

## 核心原则

**不是"关掉没用的东西"——是"精确识别高频、不可见、零用户价值的组件，将其从调度器中移除"。**

一刀切关整个子系统是粗糙操作——会把Polymarket雷达（与BTC无关的AI/科技监控）随BTC系统一起误杀。

## 三步识别法

### Step 1: 真实成本核算

不能用"印象"估算频率。必须从cron定义中提取实际频率。

**翻车案例**：BTC子系统印象中"~300次/周"，实际1,399次/周（4.66×低估）。两个15分钟看门狗（各672次/周）占总量96%，但从未被单独质疑过。

正确做法：逐个cron读schedule字段→乘以周运行次数→按投递方式分组：
- `deliver=origin`：用户可见，有价值
- `deliver=local`：用户不可见，需追问"谁在消费这个输出？"
- `deliver=weixin`：直接推送，有明确用户意图

### Step 2: 区分"全系统关闭"vs"组件关闭"

不要问"BTC系统该关吗"，要问：

| 问题 | 判断 |
|------|------|
| 该cron的输出用户是否可见？ | local→不可见→候选 |
| 可见则是否有实质价值？ | 用户说过"测试用"→降级 |
| 是否被其他cron消费？ | 无下游消费者→候选 |
| 关闭后是否产生僵尸依赖？ | 有其他cron依赖其输出→先清理依赖 |

**反模式**：主系统有LLM分析价值（虚拟量化每8h生成报告→用户可见），但看门狗的高频自主交易对"测试用"系统无价值。正确做法是关看门狗、保留主系统降频。

### Step 3: 僵尸依赖扫描

关闭上游cron前，扫描所有cron的script/output路径——任何引用被关cron输出文件的cron都是僵尸候选。

**翻车案例**：关BTC虚拟量化→留下4个僵尸cron：
- Rubrics评估-BTC交易（读已不存在的交易报告→[SILENT]但仍消耗LLM调用）
- Rubrics评估-BTC宏观（同上）
- BTC数据源健康日检（检查已关闭的API→始终alert→仍消耗LLM）
- BTC跨源关联检测（无watchdog数据→静默失败→仍在运行）

## 石油目标识别清单

以下特征叠加越多，越接近"石油目标"：

| 特征 | 含义 |
|------|------|
| 频率 >100次/周 | 高频调度消耗 |
| deliver=local | 用户从未看到输出 |
| no_agent=True | 零LLM token但消耗调度器/CPU/API配额 |
| 输出被谁消费？→无人 | 纯沉没成本 |
| 属于"测试用"子系统 | 用户已声明可关闭 |

## 三级操作

| 级别 | 操作 | 示例 |
|:--:|------|------|
| 🔴 关闭 | 零用户价值且无下游依赖 | BTC看门狗（672次/周） |
| 🟡 降频 | 有边际价值但频率过度 | BTC虚拟量化3x→1x/天 |
| 🟢 脱钩 | 被错误归类的独立组件 | Polymarket雷达从BTC清单移除 |

## 验证清单

- [ ] 真实频率已从cron schedule计算（非印象）
- [ ] 每个候选按投递方式分组
- [ ] 全系统关闭vs组件关闭已区分
- [ ] 僵尸依赖已扫描
- [ ] 误归类组件已脱钩
- [ ] 关闭后用`cronjob action=disable`而非删除（保留回滚能力）
