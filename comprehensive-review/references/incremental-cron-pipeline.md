# 增量蒸馏 Cron 管道设计模式

## 场景

需要对新内容（公众号文章/RSS/API数据）做"检测→筛选→判断→蒸馏"的增量处理管道。典型需求：每天扫描新文章，识别有价值的内容，蒸馏到知识库。

## 核心模式：两层分工

```
┌─────────────────────────────────────────┐
│ Layer 1: 脚本（no_agent / 数据收集）      │
│  - 查询增量                                    │
│  - 关键词分类 + 基础筛选                        │
│  - 输出候选池（含全文 + 元数据）                  │
│  - 阈值设为宽松（宁可多捞不少漏）                 │
└───────────────┬─────────────────────────┘
                │ CANDIDATES_START...CANDIDATES_END
                ▼
┌─────────────────────────────────────────┐
│ Layer 2: Agent（语义判断）                 │
│  - 加载领域 skill                           │
│  - 对照已有框架，判断语义增量                     │
│  - 输出：✅蒸馏 / ⏭️已蒸馏 / ⏭️跳过 + 理由     │
│  - 去重检测：避免推荐已蒸馏内容                  │
└─────────────────────────────────────────┘
```

## 关键设计决策

### 为什么不全放在脚本里？

Python 脚本能做关键词计数，做不了"这篇文章和已有 skill 有没有语义重叠"的判断。强行在脚本里做蒸馏推荐 = 假精确的橡皮章。

### 为什么不全放在 agent 里？

数据捞取（SQL 查询 + HTML 解析 + 状态管理）不需要 LLM。用 no_agent cron 省 token，只把需要判断的内容交给 agent。

### 分界线在哪？

答案是：**分在"能编码为确定性规则"和"需要语义理解"之间。**

| 脚本层（确定性规则） | Agent 层（语义理解） |
|------|------|
| SQL 增量查询 | "这篇文章对 skill 有没有增量" |
| HTML→纯文本提取 | "与已有蒸馏文章是否重叠" |
| 关键词计数 + 分类 | "应该蒸馏到哪个支柱" |
| 状态持久化 | "蒸馏后的内容应该怎么写" |
| 候选池输出（全文） | 最终用户推送格式 |

## 全文注入 vs 预览截断的教训

**初始设计**：代理只传 200 字预览 → 节省 token。

**问题**：文章的核心方法论常常在导语之后。200 字预览截断了关键内容，"如何定义黑天鹅"的关联方方法论在第 5 句之后才出现。

**修正**：deepseek-v4-flash 上下文 128K token。10 篇候选 × 2000 字 + skill 正文 ≈ 26K token，只占 20%。直接传全文，零截断。

**规则**：不要为了省 token 牺牲判断质量。先算 token 上限，再决定截断策略。如果全文在窗口内装得下，就不截断。

## 去重检测：防止已蒸馏内容重复推荐

Agent prompt 必须包含"先检查核心论点是否已在 skill 中覆盖"的指令。否则每次 cron 跑都会把已蒸馏文章重新标记为"推荐蒸馏"→ 消耗用户注意力。

回测发现：二姐最近 10 篇中有 4 篇已蒸馏。没有去重检测的话 40% 是噪音。

## 状态管理的坑：save_state 在输出之前

```
# ❌ 错误顺序
save_state(state)     # 先保存
for art in candidates:
    print(art)        # 再输出 → 如果这里崩溃，状态已更新但用户没收到通知

# ✅ 正确：在输出循环之前 save_state 没问题，但要确保输出循环不会崩溃
```

2026-07-11 慕云思辩蒸馏脚本崩溃实例：`save_state` 在第 134 行执行成功（last_distilled_id 从 1653 更新到 1902），但第 150 行 `extract_tag_words` 未定义导致 NameError 崩溃。结果：6 篇文章的状态被"消费"了但蒸馏推荐从未送到用户手上。

**防御**：
- 在输出循环中做 defensive coding（函数存在性检查、try/except 包裹）
- 或者：先输出 → 再 save_state（但如果输出后立即崩溃，状态不会更新，下次会重复推荐）
- **最优方案**：dry-run 验证所有代码路径后再上生产

## 多脚本并行维护的坑：copy-paste 传播

三个蒸馏脚本（muyun/erjie/earletf）从同一模板衍生。v1.3.0 给 muyun 加了 `extract_tag_words` 函数，但定义只在一个脚本里正确保留，其他两个脚本有引用无定义——结果就是定时炸弹：函数被调用的条件（有方法论文章）一满足脚本就崩。

**防御**：
- 共享逻辑抽取为公共模块（如 `distill_common.py`），不复制粘贴
- 如果必须独立副本，每次改动后在所有副本上跑 dry-run

- **涉及脚本**：muyun_incremental.py, erjie_incremental.py, earletf_incremental.py
